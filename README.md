## ✅ Этап 2: «Проработка моделей данных»
### Модели данных и API
#### Реализована архитектура базы данных, REST API с документацией и разграничением прав доступа.

### 👤 Пользователи
* **Авторизация:** по Email (поле username отключено).
* **Роли:** разделение на «Покупателя» и «Магазин» (type) для ограничения импорта прайсов.
* **Профиль:** добавлены поля компании и должности.
### 📦 Товарный каталог
* **Структура:** реализована связь «Один ко многим» между базовым товаром (Product) и его конкретным предложением от магазина (ProductInfo).
* **Характеристики:** Для хранения технических характеристик (Цвет, Память, Диагональ) используется гибкое поле JSONField characteristics. Это позволяет хранить произвольные пары "ключ-значение" без создания дополнительных таблиц, что ускоряет разработку и запросы к БД.
  - Пример данных: {"Цвет": "Золотистый", "Память": "256 Гб"}.
* **Связи:** Категории привязаны к магазинам через Many-to-Many.
### 🛒 Заказы
* **Жизненный цикл:** статусы от корзины до доставки.
* **Контакты:** отдельная модель адресов и телефонов покупателя.
* **Логика:** сумма заказа рассчитывается динамически в Python. Цены закупки скрыты от публичного API.
### ⚙️ Backend (DRF)
* **Оптимизация:** настроен select_related/prefetch_related. Ошибки N+1 запросов устранены.
* **Права:** публичный просмотр каталога; доступ к заказам/контактам только после авторизации.
* **Админка:** все модели доступны в Django Admin с удобными инлайнами.
### 📄 Документация
* **Интерактивный Swagger UI доступен по адресу /docs/. Генерация схемы OpenAPI автоматическая.**


## ✅ Этап 3: Реализация импорта каталога 📦

#### Реализована автоматическая загрузка прайс-листов от поставщиков через YAML-файл (`shop1.yaml`) с помощью кастомной Management Command.

### Логика работы скрипта `import_shop`
*   **Очистка:** Перед каждой заливкой удаляются старые предложения конкретного магазина во избежание дублей цен.
*   **Связи M2M:** Категории динамически привязываются к магазину при импорте.
*   **Оптимизация N+1:** В сериализаторах настроен `prefetch_related`, что исключает каскадные запросы к БД при выводе списка товаров.
*   **Гибкость характеристик:** Параметры товара хранятся в JSONField, что позволяет добавлять новые атрибуты без изменения структуры SQL.

### Как протестировать импорт
Убедись, что файл `shop1.yaml` лежит в корне проекта (рядом с `manage.py`).

1.  Запусти команду загрузки:
```bash
    python manage.py import_shop
 ```
2.  Ожидаемый результат в консоли:
```
    > Удалено старых предложений: X
    > Создано новых предложений: Y
```
3.  Проверка API:
    * Открой [http://127.0.0.1:8000/api/v1/offers/](http://127.0.0.1:8000/api/v1/offers/) или документацию Swagger `/docs/`. Должен отобразиться список товаров из файла.



## ✅ Этап 4: Реализация API views (Базовая часть)
### Реализована полная цепочка оформления заказа через REST API с авторизацией по JWT.
### Ключевые эндпоинты:

* **/api/v1/register/** — регистрация пользователя с отправкой Email о подтверждении регистрации (сигнал Django).
* **/api/v1/token/** — получение токенов доступа (access) и обновления (refresh).
* **/api/v1/contacts/** — управление контактами покупателя (адресами доставки). Созданные контакты автоматически привязываются к текущему пользователю.
* **api/v1/offers/** — публичный просмотр прайса от всех магазинов.
* **/api/v1/orders/add-to-basket/** — добавление товара в корзину (custom action). Если корзина не существует, она создается со статусом "basket". Позиции суммируются при повторном запросе на тот же товар.
* **api/v1/orders/{id}/confirm/** — подтверждение заказа владельцем. Статус меняется на "confirmed" только если заказ принадлежит текущему пользователю (защита прав доступа).
* **/api/v1/orders/** — история заказов. Пользователь видит только свои заказы благодаря фильтрации queryset.

### Особенности реализации:

* **Безопасность:** подтверждение чужого заказа запрещено на уровне ViewSet методом проверки поля order.buyer != request.user.
* **Уведомления:** при создании заказа отправляется письмо клиенту с составом покупки (добавлено в метод perform_create OrderViewSet).
* **Фильтрация:** все приватные данные скрыты за авторизацией; пользователи видят только свои контакты и заказы.
